# VERDIS M1 Sales Deep Flow Design

## 1. Objective

Implement the persistent M1 Sales flow as the second vertical slice of the VERDIS Cooperative Pilot, reusing the proven Receipts architecture without creating a universal movement wizard prematurely.

The flow is:

`DADOS → COMPROVAÇÃO → CONFERÊNCIA → CONCLUIR`

The canonical M1 scenario is:

- material: PET
- available stock: 3,200 kg
- quantity sold: 1,000 kg
- buyer: Comprador Demo
- registered unit price: R$ 3.10/kg
- registered total: R$ 3,100.00
- projected stock: 2,200 kg
- document unit price: R$ 3.20/kg
- document total: R$ 3,200.00
- difference: +R$ 0.10/kg, +R$ 100.00, +3.23%
- final decision in the canonical divergence case: keep registered values
- final stock: 2,200 kg
- document: `Documento_Venda_1279.pdf`

## 2. Product principles

1. Sales reuse the same Evidence Engine and visual system as Receipts.
2. `movement` remains the operational source for movement type, quantity, material, lifecycle status and stock effect.
3. `sales` stores buyer, commercial unit price, generated total and fiscal document reference.
4. The frontend may calculate projections but never writes stock ledger entries directly.
5. AI/extraction interprets documents; documents remain evidence. Extraction never silently changes canonical sale data.
6. Human resolution is persisted separately from extraction.
7. Healthy document processing is not a pending item.
8. Posted sales are read-only and must reconstruct their conclusion from durable backend facts after refresh.
9. The database rechecks stock at confirmation time even when the frontend already blocked an insufficient-stock sale.
10. No new visual family, palette, icon system or shell is introduced.

## 3. Existing model reused

`public.sales` already provides:

- `movement_id`
- `buyer_counterparty_id`
- `material_id`
- `quantity_kg`
- `unit_price`
- generated `total_amount`
- optional `fiscal_document_id`
- `sold_at`

The existing consistency trigger requires the sale scope, material and quantity to match the linked `movement`, and posted/voided linked sales are immutable.

The new flow must preserve those invariants instead of duplicating them in the UI.

## 4. Flow architecture

### 4.1 SaleDraftService

The draft is a coherent pair:

`movement(type=sale, status=draft) + sales`

Editable wizard fields:

- buyer
- material
- quantity
- unit price
- date/time

`total_amount` is never directly editable. It is generated by the database from `quantity_kg * unit_price`.

The draft service also loads current stock for the selected material and returns a projection for UX.

### 4.2 Shared evidence infrastructure

The Storage/hash/rollback sequence should be reused from Receipts through a generic evidence upload core when that extraction can be done without changing receipt behavior.

Sale-specific registration stays in a sale RPC because claimed fields differ from Receipts.

Transient upload states remain client-only:

- none
- selected
- uploading
- uploaded
- failed

Durable facts are document/evidence rows and extraction state.

### 4.3 SaleConferenceService

Conference is read-only and derives a view model from:

- movement
- sale
- evidence
- document
- latest document extraction

States:

- `registered_only`
- `processing`
- `match`
- `divergence`

The service must never invent extracted values when a document is only processing.

`match` uses the UI copy `Dados coincidentes`, never `validado`, `certificado` or `auditado`.

### 4.4 ConfirmSaleService

The frontend confirmation adapter calls only `confirm_sale_m1(...)`.

It does not directly update:

- `sales`
- `movements`
- stock ledger
- validations

### 4.5 SaleCompletionService

For posted sales, the conclusion must reconstruct from durable facts:

- movement
- sale
- operator validation/resolution
- evidence/document
- stock ledger/current stock

The result must survive page refresh and not depend on volatile React state.

## 5. Canonical data and divergence model

Registered facts for the canonical scenario:

```json
{
  "quantity_kg": 1000,
  "unit_price": 3.10,
  "total_amount": 3100
}
```

Documentary facts:

```json
{
  "quantity_kg": 1000,
  "unit_price": 3.20,
  "total_amount": 3200
}
```

Evidence preserves both sides:

- `claimed_fields`: quantity, unit price, total at registration time
- `extracted_fields`: quantity, unit price, total from document extraction

Derived difference shown by the UI:

- unit price difference: +R$ 0.10/kg
- total difference: +R$ 100.00
- percent difference: +3.23%

No decision is preselected.

## 6. Decisions

Supported logical decisions:

- `registered_only`
- `use_document`
- `keep_registered`

### `registered_only`

Used when no usable extraction exists. It confirms the sale with the registered commercial values and must not manufacture an accepted validation or evidence upgrade.

### `use_document`

Requires a real processed extraction. The transaction adopts the extracted unit price. Because `sales.total_amount` is generated, the total changes atomically with unit price.

For the canonical scenario:

- unit price becomes R$ 3.20/kg
- total becomes R$ 3,200.00

### `keep_registered`

Requires a real processed extraction when the flow is resolving a documentary divergence. If documentary commercial values differ from registered values, a nonblank justification is mandatory.

For the canonical scenario:

- unit price remains R$ 3.10/kg
- total remains R$ 3,100.00
- operator reason is persisted

Validation rule codes:

- `SALE_USE_DOCUMENT_PRICE`
- `SALE_KEEP_REGISTERED_PRICE`

## 7. Evidence registration RPC

Create `register_sale_evidence_document(...)`.

Responsibilities:

1. derive actor from `auth.uid()`;
2. lock/load movement and linked sale;
3. require `movement_type = sale`;
4. require `status = draft`;
5. enforce scope permissions including evidence upload;
6. validate filename, MIME type, SHA-256 and scoped Storage path;
7. atomically create document + evidence;
8. persist claimed fields `{quantity_kg, unit_price, total_amount}`;
9. set document type/evidence type for sales;
10. associate the resulting document with `sales.fiscal_document_id` when safe;
11. return `document_id` and `evidence_id`.

Storage object upload happens before the RPC. If the RPC fails, the frontend performs compensating Storage deletion.

## 8. Confirmation RPC

Create `confirm_sale_m1(...)`.

Suggested inputs:

- `p_movement_id uuid`
- `p_decision text`
- `p_evidence_id uuid default null`
- `p_reason text default null`

Return:

- `movement_id`
- `sale_id`
- `adopted_quantity_kg`
- `adopted_unit_price`
- `adopted_total_amount`
- `previous_stock_kg`
- `new_stock_kg`

Transaction requirements:

1. derive actor from `auth.uid()`;
2. lock the movement and sale;
3. require sale movement and draft status;
4. enforce `sale.create`/required scope permission server-side;
5. calculate current stock inside the transaction;
6. reject confirmation when sale quantity exceeds current stock;
7. validate the decision;
8. for `use_document`/`keep_registered`, require a real extraction row associated with this sale evidence;
9. validate documentary `unit_price` as nonnegative and documentary quantity/total as coherent enough for comparison;
10. for `keep_registered` with divergence, require nonblank reason;
11. persist operator validation only for documentary resolution decisions;
12. for `use_document`, update `sales.unit_price`; generated total updates automatically;
13. preserve quantity, buyer and material unless a later separately designed flow explicitly supports changing them;
14. set movement status to `posted`;
15. rely on the existing posting/ledger mechanism as sole stock writer;
16. return authoritative before/after stock and final commercial values;
17. reject a second confirmation and create no duplicate ledger effect.

## 9. Stock semantics and concurrency

### Data step projection

The frontend shows current stock and projected stock.

Canonical sufficient case:

- current: 3,200 kg
- sale: 1,000 kg
- projected: 2,200 kg
- CONTINUAR enabled when other required fields are valid

Canonical insufficient case:

- current: 320 kg
- sale: 400 kg
- unit price: R$ 3.10/kg
- total calculation: R$ 1,240.00
- projected stock label: `Indisponível`
- CONTINUAR disabled

The total remains visible because it is a commercial calculation, but the sale cannot progress as a valid stock operation.

### Confirmation-time recheck

Even if the frontend originally saw enough stock, `confirm_sale_m1` must re-evaluate current stock before posting.

If stock changed concurrently and is no longer sufficient, the transaction fails without posting or partial ledger effect.

User-facing copy should state that stock changed and the quantity must be reviewed; internal SQL details are not exposed.

## 10. Route and resume behavior

Routes:

- `/vendas/nova?step=dados`
- `/vendas/nova/:movementId?step=comprovacao`
- `/vendas/nova/:movementId?step=conferencia`
- `/vendas/nova/:movementId?step=concluir`

The URL represents navigation intent, while durable backend state constrains editability.

Precedence:

1. posted movement → always `concluir` read-only;
2. draft + processed unresolved divergence → conference divergence;
3. draft + document processing → proof or conference according to allowed query intent;
4. draft + no document → data/proof/conference according to allowed query intent;
5. bootstrap route without movement id → data.

Transient file-selection/upload-progress state may be lost on refresh. Durable draft, document, evidence, extraction and decision facts are reconstructed.

## 11. Exact UI states

### VEN-03A Dados

Fields:

- Comprador
- Material
- Quantidade
- Preço unitário
- Data e hora

Derived display:

- valor total
- saldo atual
- saldo projetado or `Indisponível`

### VEN-03B Comprovação empty

Actions:

- TIRAR FOTO
- ENVIAR ARQUIVO
- CONTINUAR SEM DOCUMENTO

### VEN-03C Selected

Display filename/type/size and `Pronto para enviar`.

Actions:

- ENVIAR DOCUMENTO
- ordinary continue remains unavailable until upload succeeds or user explicitly chooses no document

### VEN-03D Uploading

Display `Enviando`; disable conflicting actions.

### VEN-03E Uploaded/processing

Display:

- Documento enviado
- Processando
- VISUALIZAR DOCUMENTO
- CONTINUAR

Normal processing is not a pending item.

### VEN-03F Upload failed

Actions:

- TENTAR NOVAMENTE
- Trocar arquivo
- Tirar outra foto
- CONTINUAR SEM DOCUMENTO

Draft remains intact.

### VEN-04A Processing/registered only

Display only registered commercial values and document processing state. Do not display invented extracted values.

Confirmation uses `registered_only`.

### VEN-04B Match

Display `Dados coincidentes`.

### VEN-04C Divergence

Canonical display:

- registrado R$ 3.10/kg / R$ 3,100
- documento R$ 3.20/kg / R$ 3,200
- +R$ 0.10/kg
- +R$ 100
- +3.23%

Actions:

- USAR VALORES DO DOCUMENTO
- MANTER VALORES REGISTRADOS

Neither starts selected.

### VEN-04D Justification

When `keep_registered` resolves a documentary divergence, show required textarea and keep confirm CTA disabled until `reason.trim().length > 0`.

### VEN-05 Conclusion

Canonical conclusion:

- Venda #1285 presentation label
- PET
- 1,000 kg
- Comprador Demo
- final unit price R$ 3.10/kg
- final total R$ 3,100
- stock 3,200 → -1,000 → 2,200
- `Documento_Venda_1279.pdf`
- document processed
- decision `Mantidos valores registrados`
- persisted justification when applicable

Posted sale is read-only.

## 12. Late extraction after posting

A late extraction must never rewrite a posted sale.

If documentary divergence is discovered after posting:

- canonical movement/sale values remain immutable;
- the system may surface a human-review requirement in a later dedicated review/pending increment;
- any commercial or stock correction must be a new explicit correction/adjustment flow, not mutation of the posted sale.

This increment does not implement the later adjustment workflow.

## 13. Error behavior

- draft save failure: retain entered form values and remain editable;
- upload failure: preserve draft and selected file for retry where possible;
- Storage upload succeeds but registration RPC fails: compensating delete of uploaded object;
- extraction processing: allow continuation with registered values;
- invalid/missing extraction for documentary decision: server rejects documentary decision;
- insufficient stock at final confirmation: server rejects atomically; movement remains draft;
- double confirmation: server rejects; no duplicate stock effect;
- scope/auth failure: propagate a user-safe operation failure and do not partially mutate business state.

## 14. Reuse boundaries

Reuse existing AppShell, tokens, Breadcrumb, PageHeader, Button, StatusBadge, stepper layout and evidence-upload presentation.

Extract generic document upload infrastructure only where this can be done without changing the behavioral contract of Receipts.

Keep sale-specific services separate:

- SaleDraftService
- SaleConferenceService
- ConfirmSaleService
- SaleCompletionService
- SaleFlowPage

Do not refactor both flows into a universal `MovementFlow` in this increment.

## 16. Acceptance criteria

The increment is complete only when:

- all VEN-03A through VEN-05 states are implemented;
- canonical 3,200 → -1,000 → 2,200 sale is functional;
- insufficient 320/400 case is blocked in UI and server-side;
- documentary divergence 3.10 vs 3.20 is represented neutrally;
- price and generated total change together for `use_document`;
- keep registered requires justification;
- no extraction silently modifies sale data;
- processing does not create a pending item;
- posted sale reopens in Concluir/read-only and reconstructs durable summary;
- frontend never writes stock ledger directly;
- one posted sale creates exactly one ledger effect;
- Receipts regression remains green;
- web tests, typecheck, build, pgTAP and generated database types all pass on the final SHA.

## 17. Out of scope

This increment does not implement:

- fiscal invoice issuance;
- accounts receivable;
- bank/payment integrations;
- freight/logistics;
- discounts/tax calculations;
- multi-item sales;
- cancellation of posted sales;
- automatic financial correction;
- late-extraction adjustment workflow;
- mobile redesign;
- final OCR/AI provider implementation.
